# Оптимизация фоновой синхронизации InControl

Изменения от 10 ноября 2026 года. Рабочий код изменён только в `app.py`.
Тесты добавлены в `tests/test_incontrol_sync_performance.py`.

## Что изменилось

- Импорт по-прежнему запускается в 00, 15, 30 и 45 минут каждого часа.
- Обновление меток запускается в 07 и 37 минут каждого часа. Часовой пояс — Москва.
- Оба обхода используют одну именованную блокировку MySQL. Если обход ещё
  выполняется, второй плановый запуск пропускается без ожидания и записывает
  причину в журнал. Повтор произойдёт при следующем плановом запуске.
- Блокировка удерживается отдельным физическим соединением и снимается
  на нём же. Между взятием блокировки и сетевыми запросами выполняется commit:
  это соединение не удерживает открытую транзакцию данных сайта. Само выделенное
  соединение остаётся занятым до конца задания — оно нужно для mutex.
- ORM-соединения возвращаются в пул до обращений к InControl. Запросы к БД
  и записи выполняются отдельными короткими этапами между сетевыми вызовами.
- Кеш меток больше не очищается перед сетевым обходом. После получения ответов
  перечитываются текущие активные заявки и одной транзакцией заменяются только
  успешно проверенные борта. Данные недоступной организации сохраняются.
- Для борта с неизвестным парком частичный ответ организаций не считается
  доказательством отсутствия заявок. Его прежний кеш сохраняется до полного ответа.
- Метки бортов, у которых больше нет активных заявок сайта, очищаются при
  успешном обновлении. При ошибке записи вся замена откатывается.
- Уже импортированные id отбираются пакетами до точечных сетевых проверок.
  В тесте с 80 известными заявками отбор выполнил 2 SQL-запроса и не запросил
  подробности ни одной из этих заявок.
- После получения подробностей выполняется повторная проверка локальной БД,
  чтобы учесть заявку, открытую вручную за время внешнего запроса. Это сохраняет
  прежнюю защиту от повторного открытия; схема БД и ручное создание не менялись.
- HTTP-сессии клиентов закрываются при успехе и ошибке.

## Выкладка

Новых таблиц, колонок, Python-зависимостей и SQL-команд для этого изменения
не требуется. На сервере нужно обновить `app.py` и перезапустить приложение
обычным способом. Ранее добавленные файлы проверки закрытия остаются нужны.
Эта правка внесена локально; выкладка на рабочий сервер не выполнялась.

## Замеры после запуска

В `logs/app.log` появились строки с префиксом `INCONTROL_SYNC`:

```text
INCONTROL_SYNC job=cache total_ms=... fetch_ms=... write_ms=... checked=... skipped=... failed_orgs=...
INCONTROL_SYNC job=import total_ms=... fetch_ms=... db_ms=... created=... skipped=... errors=...
```

`total_ms` — всё время обхода; `fetch_ms` — время внешних запросов;
`db_ms` — суммарное время локального отбора и записи импорта;
`write_ms` — время чтения актуальных бортов и замены кеша.
Это длительности этапов, а не только исполнения SQL на сервере.
Замеры относятся к начавшим выполняться обходам; пропущенные из-за mutex
запуски отмечаются отдельной строкой.

Перенос сети за границы транзакций уменьшает влияние долгих ответов InControl
на локальную БД. Он не гарантирует ускорения самого внешнего сервиса.
Фактическое изменение скорости рабочего сайта нужно оценить по новым логам.

## Проверка

27 новых тестов синхронизации и 34 теста ранее сделанного закрытия — прошли.
Внешние системы и рабочая база не вызывались. Проверены:

- отсутствие ORM-сессии при аутентификации, обходе и загрузке подробностей;
- сохранение прежнего кеша во время сети и при сбое парка;
- атомарный откат при ошибке записи;
- ручное создание/закрытие заявки во время внешнего запроса;
- повторный импорт, пакетный отбор известных id и несколько новых заявок;
- исключение ТО из импорта, перепроверка закрытых/отклонённых заявок;
- сохранение времени создания InControl и данных электробуса;
- продолжение импорта других парков при сбое одного;
- снятие блокировки на исходном соединении после ORM remove/commit;
- освобождение блокировки и откат незавершённой записи при ошибке;
- отбрасывание соединения при ошибке RELEASE_LOCK;
- сохранение интервала импорта и новое расписание меток.

В полном наборе после изменения рабочего кода: 74 прошли, 31 старый сбой
остался прежним; новых сбоев по сравнению с предыдущим состоянием не было.
После этого добавлены ещё 4 теста только в новый тестовый файл; все 61 тест
синхронизации и закрытия прошли вместе. Полный набор повторно не запускался,
поскольку рабочий код после полного запуска не менялся.

Среда: Python 3.13, SQLite в памяти; функции блокировок MySQL проверены
контролируемой подменой соединения. Нагрузочный тест живого MySQL/Passenger
и фактическое время ответа InControl не измерялись.

Свойства именованных блокировок сверены с [документацией MySQL](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html):
commit не снимает GET_LOCK; RELEASE_LOCK должен выполняться той же сессией.
Обращение с повреждёнными соединениями соответствует [документации SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/pooling.html).

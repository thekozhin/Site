# Отклонение InControl — 14.11.2026

## Результирующая схема

При отклонении подписывается только **заявка на ремонт**. Акт на ремонт не формируется и не подписывается. Это подтверждено реальным тестом и уточнением пользователя.

1. Кнопка «Отклонить» на /complete_task/<id> сохраняет черновик completed_work и запускает фоновый процесс.
2. Проверяются личный аккаунт, фамилия и UUID, борт, парк, основная и связанные задачи, обратные связи и доступность полей.
3. Связанные задачи переводятся в «Отклонено», результат каждой перечитывается.
4. Основная переводится в «Принято», user_performer_id — UUID личного аккаунта.
5. Пользователь нажимает «Подписать заявку». auth/signature либо возвращает sign_code, либо отправляет код по почте; поле появляется только во втором случае.
6. После подтверждения подписи основная переводится в «Отклонено» и поле «Причина отклонения» получает completed_work.
7. После проверки итогового этапа, причины и подписи доступно «Сохранить отклонение на сайте». Этот POST закрывает локальную заявку с reject=True.

Кнопка «Завершить» продолжает работать по прежней проверке: новая схема выполнения не подключена.

## Привязка и защита

Поле «Основная заявка InControl» заполнено привязанным incontrol_task_id; если привязки нет, пользователь указывает номер явно. Номер проверяется по борту, парку и прямым/обратным связям.

Причина фиксируется на время процесса. После начала удалённых изменений менять её автоматически нельзя. До любых изменений ошибку предварительной проверки можно исправить в форме. Возврат к форме восстанавливает черновик. Чужого назначенного исполнителя процесс не заменяет. Личный аккаунт берётся из incontrol_account текущего пользователя; общего аккаунта как запасного нет.

Состояние и JWT зашифрованы в incontrol_rejection_run. Код из письма в БД не сохраняется. Уникальные task_id и remote_id препятствуют запуску двух процессов для одной заявки. Внешние HTTP выполняются фоновым потоком без удержания ORM-транзакции. Ограничено двумя параллельными цепочками на процесс.

Нет автоматических повторов POST/PATCH при сетевой ошибке. Повторный запуск сначала перечитывает этапы и подпись актуальной версии документа. Подпись привязана к шагу и версии документа. Результат предыдущей версии заявки не подтверждает подпись новой. Ошибка оставляет локальную заявку открытой. После начала отклонения нельзя переключить локальное закрытие на «Выполнено».

## Установка

Предварительно установить личные настройки InControl из docs/incontrol-personal-completion.md, включая cryptography==50.0.2 и таблицу incontrol_account.

1. Создать таблицу через docs/migrations/2026-11-14-incontrol-rejection.sql либо `flask --app app init-incontrol-rejections`. Этот SQL в рабочей MySQL автоматически НЕ выполнялся.
2. Обновить app.py, добавить incontrol_rejection.py и incontrol_rejection_jobs.py, обновить incontrol_accounts.py и templates/complete_task.html, добавить static/js/incontrol-inline.js. Остальные файлы личных настроек должны быть уже установлены.
3. В серверном .env задать INCONTROL_REJECTION_ENABLED=1 и перезапустить приложение. По умолчанию цепочка выключена до установки таблиц. SECRET_KEY должен совпадать у всех воркеров и не меняться после сохранения настроек. Не отключать цепочку, пока остаются незавершённые отклонения.
4. В шестерёнке каждый пользователь сохраняет личные данные InControl.

Страницу процесса можно обновлять/открывать в другом воркере. Через три минуты прерванную обработку можно возобновить кнопкой проверки состояния. Удалять строку процесса после частичного изменения удалённых задач нельзя — она нужна для продолжения.

## Реальный тест 162758

Разрешён пользователем: основная 21464788, связанная 21464800, completed_work = «Борт на линии». Исходно обе были в «Назначено», исполнитель основной отсутствовал.

Подтверждены переходы связанной в «Отклонено», основной в «Принято», назначение личного исполнителя, подпись заявки, затем основная в «Отклонено» и причина «Борт на линии». Пользователь ввёл код в локальной форме и подтвердил корректное закрытие в InControl. Акт отсутствует по правилам отклонения; его ожидание удалено из реализации.

Локальный тестовый UI использовал SQLite, а API — реальный InControl. Заявка в рабочей базе setrans этим тестовым UI не закрывалась. Для установки на рабочем сайте нужно загрузить перечисленные файлы, применить миграцию и включить флаг.

Профильные тесты: 38 пройдены. Полный контрольный прогон: 32 failed, 166 passed in 2.89s. Новых падений относительно baseline нет.

Личный JWT/refresh-сеанс дополнительно сохраняется зашифрованным в incontrol_account и переиспользуется между разными заявками. При смене логина/пароля сеанс сбрасывается. Это не таймер 12 часов: необходимость кода определяет сервер InControl.

Итоговая проверка локальной страницы процесса после исправления: «Заявка на ремонт подписана. Отклонение и причина в InControl подтверждены». Данные тестового процесса сохранены в локальной SQLite, рабочая база setrans не изменялась.

## Автоматический поиск и повторный тест — 164466

При любом отклонении в поддерживаемом парке выполняется поиск открытых основных заявок по точному борту и парку, с полной пагинацией и проверкой типа работ. Номер вручную больше не нужен. Привязанный incontrol_task_id используется только для однозначного выбора среди найденных. Ошибки, таймауты и некорректные ответы не считаются отсутствием заявки. При отсутствии всех открытых заявок сохраняется результат no_remote; локальное отклонение разрешено только для того же пользователя/формы и в течение 90 секунд. При наличии заявки выполняется цепочка отклонения с одной подписью. Случай нескольких непривязанных заявок останавливается для ручного выбора.

remote_id в таблице процесса теперь допускает NULL, пока поиск не завершён. Для ранее созданной таблицы с NOT NULL выполнить `ALTER TABLE incontrol_rejection_run MODIFY remote_id BIGINT NULL;`. Для таблицы, созданной актуальным SQL, это не требуется. В используемой локальным процессом MySQL таблица создана сразу с NULL.

Тест выполнен через http://127.0.0.1:5001/complete_task/62135: борт 164466, 1 парк, основная 21467425, связанные 21467430 и 21467433. После нажатия «Отклонить» поиск нашёл основную заявку. Подпись подтвердил пользователь. После подтверждения удалённого отклонения сохранено локальное: task.status=completed, reject=True, completed_work=«Борт на линии», процесс consumed.

Локальный сервер использует MySQL из .env, а не отдельную тестовую SQLite. Сохранение в интерфейсе изменило эту реальную запись. Адрес 127.0.0.1 относится к интерфейсу, а не к месту хранения данных.

Исправлено переключение парка при устаревшем session.available_parks: /set_park сверяет права с current_user.allowed_parks и обновляет разрешённый список сессии. Права сверх сохранённых в users не добавляются.

## Сеанс подписи

Добавлен incontrol_session.py. Личный сеанс теперь сохраняется целиком: access/refresh и cookies сервера с доменом, путём, secure и expires, зашифрованными в учётной записи/процессе. После ответа API, включая подпись, изменения сеанса сохраняются. Истёкшие cookies отбрасываются. Токен не обновляется принудительно перед каждым шагом, если ещё действителен. Введённый код подписи отдельно не сохраняется.

Это исправляет известные недостатки хранения сеанса, которые могли приводить к повторному запросу кода. Реальное отсутствие повторного письма в течение 12 часов пока не проверено: для этого нужна следующая разрешённая заявка. Срок подтверждения по-прежнему определяет InControl, а не локальный таймер.

Для установки этого продолжения дополнительно добавить incontrol_session.py и обновить incontrol_accounts.py, incontrol_rejection.py, incontrol_rejection_jobs.py, app.py, templates/complete_task.html, static/js/incontrol-inline.js. Текущий локальный процесс на 5001 запущен с RUN_SCHEDULER=0, SESSION_COOKIE_SECURE=0, INCONTROL_ENABLED=1, INCONTROL_REJECTION_ENABLED=1. Для HTTPS рабочего сервера SESSION_COOKIE_SECURE должен оставаться 1.

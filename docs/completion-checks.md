# Проверка InControl перед закрытием заявки

## Поведение

При подтверждении закрытия или отклонении заявки форма остаётся открытой.
Пользователь видит индикатор в кнопке и «Проверяем InControl…» рядом; кнопки и поля формы
временно заблокированы от повторной отправки и изменения проверяемого действия.

Если в InControl нет подходящей открытой заявки, браузер отправляет обычный
POST на закрытие с одноразовым идентификатором результата. Только этот POST
меняет статус заявки, пробег и признак сезонного обслуживания. Существующий
выбор печати и перенаправления после закрытия сохраняются.

Если открытая заявка есть, сервис недоступен, ответ некорректен или проверка
истекла, закрытие запрещено. Причина показывается обычным flash-уведомлением
справа внизу. Повторить проверку можно кнопкой завершения или отклонения.
Текст, пробег и время сохраняются.

Ремонт проверяет типы «Заявка на ремонт» и «Заявка на ремонт с линии»; ТО —
«Заявка на сервисное обслуживание». Подтверждения сезонного обслуживания и
фотографий эвакуации выполняются перед запуском проверки.

## Перед запуском обновления на сервере

Изменения подготовлены локально; выкладка на рабочий сервер не выполнялась.

В обновление должны войти:

- `app.py`;
- `incontrol.py`;
- новый `completion_checks.py`;
- `templates/complete_task.html`;
- новый `static/js/completion-check.js`.

После доставки этих файлов, из каталога проекта и с активированным рабочим
Python-окружением выполнить:

```bash
RUN_SCHEDULER=0 python -m flask --app app:application init-completion-checks
```

Команда создаёт только новую таблицу `completion_check`. Она идемпотентна:
повторный запуск не удаляет данные. Выполнить её до перезапуска HTTP-процессов
с обновлённым кодом. При отсутствии таблицы интерфейс покажет ошибку проверки,
закрытие заявки не будет разрешено.

Дополнительные Python-пакеты, Redis, Celery и отдельный демон для этой реализации
не требуются. Существующие настройки `INCONTROL_ENABLED` сохраняются. Запуск
APScheduler для проверок закрытия не нужен.

После создания таблицы перезапустить приложение обычным способом и проверить:

1. Открыть реальную форму, заполнить поля, подтвердить завершение.
2. Убедиться, что окно проверки остаётся открытым до ответа.
3. При открытой заявке InControl убедиться, что закрытие запрещено, поля сохранены.
4. При разрешающем ответе проверить закрытие и существующий выбор печати.

Тестовый стенд и подмены InControl из каталога `work/` в обновление не входят.

## Реализация и пределы

Состояние проверки хранится в общей БД. Следующий HTTP-запрос может прийти
в другой процесс Passenger и получить тот же результат. У каждого процесса
есть не более четырёх фоновых проверок без неограниченной очереди. Когда
все слоты заняты, пользователь получает предложение повторить попытку.
Количество процессов нужно учитывать при оценке общей нагрузки на InControl.

Внешний запрос выполняется без удержания соединения и транзакции БД.
При сетевой ошибке интерактивная проверка не использует вложенные повторы.
Connect timeout — до 3 секунд, read timeout — до 25 секунд; перед каждым
сетевым запросом проверяется оставшийся бюджет в 35 секунд. Это не жёсткое
прерывание потока: DNS, соединение и чтение могут выйти за этот бюджет.
Незавершённая проверка перестаёт давать результат через 45 секунд от создания;
поздний ответ не разрешает закрытие. Успешный результат действителен 60 секунд.

Проверка привязана к пользователю, заявке и её параметрам: борт, парк, тип,
статус, связь с ТО. При изменении этих параметров проверку нужно повторить.
Разрешение используется только один раз и в одной транзакции с закрытием.
Блокировка строки Task в MySQL защищает от повторного закрытия двумя запросами.

Поток сам по себе никогда не закрывает заявку. Если процесс Passenger
перезапущен или вкладка закрыта, незавершённая проверка истечёт. Повторить
её можно из формы; результат не хранится в памяти одного HTTP-процесса.
Проверки старше суток очищаются при запуске новых проверок.

При выключенном `INCONTROL_ENABLED` либо вне существующего перечня проверяемых
парков внешний запрос не выполняется, как и до изменения.

## Проверки от 10 ноября 2026 года

Новые тесты: 34 прошли. Покрыты ожидание, успешный ответ, отказ, сетевые ошибки,
истечение проверки, поздний ответ, повторное закрытие, принадлежность результата
пользователю и заявке, изменение заявки, сохранение пробега и текста при ошибке,
ТО, отклонение, печать, лимит исполнителей, CSRF, отсутствие таблицы и её
идемпотентное создание. Проверен реальный фоновый поток: пока он ждёт,
`/health` и получение состояния отвечают, а заявка остаётся открытой.

В браузере на изолированном локальном стенде подтверждены оба сценария:
ошибка интеграции сохраняет форму и оставляет заявку в ремонте; разрешающий
ответ закрывает заявку и показывает выбор печати. Использованы синтетические
данные и подмена внешнего сервиса, рабочая база и InControl не вызывались.

Полный набор: 51 тест прошёл, 31 упал. На сохранённой версии до изменения
падают те же 31 тест; новых сбоев в сравнении не обнаружено. Старые тесты
содержат несовместимые подмены HTTP-сессии и прежние предположения о схеме
кеша InControl. Их исправление не входит в это изменение.

Локальные тесты выполнены на Python 3.13 и SQLite. Поведение блокировок
MySQL, лимиты рабочего Passenger и доступность живого InControl в этом
окружении не проверялись.

Для запуска новых тестов в окружении с pytest:

```bash
RUN_SCHEDULER=0 DATABASE_URL=sqlite:///:memory: INCONTROL_ENABLED=0 \
python -m pytest tests/test_completion_checks.py tests/test_completion_incontrol_client.py -q
```

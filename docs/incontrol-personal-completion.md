# Личный аккаунт и закрытие InControl — 13.11.2026

## Реализовано

Шестерёнка справа от имени открывает /settings/incontrol. Авторизованный пользователь сохраняет и удаляет только собственные данные. Проверка входа использует сохранённые данные и IncontrolClient с interactive=True, без общей учётной записи. Пароль никогда не возвращается в HTML, cookie или журналы приложения. Логин и пароль вместе зашифрованы Fernet в отдельной таблице incontrol_account.

Ключ по умолчанию выводится из SECRET_KEY приложения с отдельным префиксом назначения. SECRET_KEY должен быть одинаковым у всех процессов и сохраняться при перезапуске; его утрата/смена требует заново ввести данные InControl. Доступ к .env означает доступ к ключу шифрования. Резервные копии базы и .env хранить отдельно. При необходимости можно задать INCONTROL_CREDENTIALS_KEY в application.config как Fernet-ключ; механизм его доставки в конфигурацию здесь не добавлялся.

На сервере:
1. Установить зависимость cryptography==50.0.2 из requirements.txt.
2. Выполнить docs/migrations/2026-11-13-incontrol-account.sql (или flask --app app init-incontrol-accounts).
3. Загрузить app.py, incontrol_accounts.py, templates/base.html, templates/incontrol_settings.html и перезапустить приложение.
4. Каждый пользователь открывает шестерёнку, сохраняет личный аккаунт и проверяет вход.

## Пока НЕ реализовано

Автоматическое изменение этапов, заполнение услуг и подписание. Существующее закрытие на setrans и проверки InControl не заменены новым процессом. Код не выполняет PATCH задач и POST подписи. Сервисная учётная запись для фонового чтения заявок остаётся независимой.

В текущем локальном .env нет учётных данных InControl, поэтому получить реальные формы/права/этапы заявок 21209079 и 21209083 не удалось. Пользователю предложено добавить INCONTROL_LOGIN и INCONTROL_PASSWORD в локальный .env для read-only исследования. Эти переменные нужны исследованию; сохранение персональных настроек не читает их как запасной аккаунт.

## Что подтверждено исходным кодом официального веб-клиента

Источник: https://skk.mttech.moscow/assets/index-DGSqPXhv.js, связанные TaskEditFormPage/TaskForm/TaskReportsPopup. Код изучен 13.11.2026, API-документация не опубликована.

- Основная задача запрашивается через GET /api/v1/tasks/{id}/.
- Общий update клиента использует PATCH задачи; форматы изменяемых полей нужно получить из реальных task/form responses.
- Связи включают parent_task и custom_field_dependent_tasks; точная цепочка для примера требует чтения данных.
- Доступные этапы запрашиваются через /api/v1/tasks/available-phases/. Нельзя переносить ID этапов между типами заявок без проверки.
- Документы и подписание — отдельный ресурс reports, POST /api/v1/reports/sign/; настройки — GET /api/v1/signature-settings/.
- Получение подписи есть в auth/signature/. Названия параметров, challenge и разрешённые действия необходимо подтвердить в личном аккаунте.

## Порядок следующего этапа

1. Под личным аккаунтом прочитать обе заявки, форму, связанные задачи, доступные этапы и документы; проверить борт/парк и права текущего пользователя.
2. Найти исполнителя по фамилии текущего пользователя. При отсутствии или неоднозначности показать выбор, не брать первого совпавшего.
3. Перед отправкой показать основную заявку, связанные задачи и completed_work. Не закрывать произвольные соседние заявки того же борта.
4. Сохранить completed_work в поле «Выполненные услуги» каждой выбранной связанной задачи; подтвердить результат чтением; перевести в «Выполнено». Проверить, что все необходимые связанные задачи завершены.
5. В основной задаче выставить исполнителя и этап «Принято»; получить актуальные документы, выполнить первую подпись.
6. Только если сервер действительно требует пароль подписи — запросить его в отдельном окне. Не считать, что он истекает строго через 12 часов. Код подтверждения не сохранять в учётных настройках.
7. Перечитать основную задачу и документы, перейти в «Выполнено», подписать второй документ; проверить итог.
8. Сохранять состояние процесса в БД между запросами/воркерами, включая ожидание кода. После таймаута проверять состояние удалённой задачи до повторной записи/подписи. Не перезапускать всю цепочку с первого шага.
9. Закрывать локальную заявку только после подтверждённого завершения удалённой цепочки. Отклонение — отдельная будущая схема.

Подписание и данные задач на реальном примере пока не проверены; описанный порядок — требования к следующему этапу, а не выполненные операции.


## Подтверждено после предоставления доступа

Личный вход успешно проверен, выполнены только GET-запросы к задачам и /me/. В коде официального клиента подтверждён PATCH задач с phase_id, user_performer_id и additional_fields: [{id, value}]. Payload изменения пока не отправлялся.

На примере 21209079:
- Тип «Заявка на ремонт», этап «Назначено.».
- Связанная задача 21209083 указана в дополнительном поле 416 «Связанные нарушения», link_type=task.
- У 21209083 есть обратная запись custom_field_dependent_tasks: linked_task=21209083, dependent_task=21209079.
- Поле «Выполненные услуги» в ней имеет ID 501.
- Связанная задача сейчас **«Отклонено.»**, поэтому пробное успешное закрытие требует другого открытого примера или явного решения пользователя по этому случаю.
- Документы конкретной заявки: GET /api/v1/tasks/{id}/available-report-files/?is_paginated=false. Общий /reports/ — каталог, а не файлы конкретной задачи.
- Официальный OTPPopup запрашивает POST /api/v1/auth/signature/ с {task_id}. Если ответ содержит sign_code, отдельный ввод не нужен; иначе интерфейс показывает ввод кода из письма. Запрос этого endpoint сам может отправить письмо, поэтому он не выполнялся при read-only исследовании.
- Подписание в официальном клиенте: POST /api/v1/reports/sign/ с {code, file_path}. Файл берётся из актуальных available-report-files. Запрос не выполнялся.

Добавлена только подготовительная проверка в incontrol_completion.py и кнопка «Проверить заявку» в личных настройках. Проверка не редактирует задачи и не подписывает документы. Проверяет выбранный парк, личную фамилию, прямые и обратные связи, текущие этапы и наличие редактируемого поля услуг. Не подменяет существующее закрытие setrans. Дополнительной таблицы для неё не нужно.

Для установки этого продолжения также загрузить incontrol_completion.py, обновлённые incontrol_accounts.py и templates/incontrol_settings.html. Личный пароль остаётся в ранее созданной таблице. Тесты подготовки и настроек: 15 проверок пройдены.

Второй предоставленный пример также прочитан без изменений: основная 21456527 (борт 164015) уже «Выполнено.», связанные 21456552, 21456570, 21456607, 21456631 тоже «Выполнено.». Во всех четырёх поле 501 заполнено текстом «Готов. Восстановление питания всех табло». На основной выбран другой исполнитель, его не меняли.
